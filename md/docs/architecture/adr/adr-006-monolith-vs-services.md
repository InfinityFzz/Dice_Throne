# ADR-006：单体 vs 微服务拆分时机

- **状态**：Accepted
- **日期**：2025-xx-xx（架构基线）
- **决策者**：程基岩（engineering-lead）
- **相关**：ADR-001（传输）、ADR-005（持久化）

## 背景

用户已定：TypeScript 全栈、Node + Socket.IO + React。lean 推进强度。MVP 只做 1v1、4 英雄。

需要决定：是「模块化单体」还是「一开始就拆服务」（例如：matchmaking 服务 / game 服务 / auth 服务 / replay 服务）。

已知约束：
- 团队规模小（1–3 人）。
- 规则引擎必须前后端同构复用（拆服务会引入调用边界）。
- 房间状态是有状态的（长连接绑定 + 内存 GameState）。

## 决策

**MVP 采用模块化单体（modular monolith）：一个 Node 进程 + pnpm workspace 的三个包（shared / server / web）。不拆微服务。**

但**必须**在 M1 前落地一个结构性前提：

> **房间 Actor 串行化**：每个房间由一个逻辑上单线程的命令队列驱动（`MatchActor`），所有对该房间的意图按顺序进入队列、串行 apply。房间之间互不共享可变状态。

这个前提决定了未来扩展的形态：
- 单进程：所有房间的 Actor 在同一个事件循环里跑，靠队列保证串行。
- 多实例：房间 Actor 被固定归属到某个实例（一致性哈希或房间路由表），**Actor 模型本身不变**。
- 因此「多实例」退化为「房间归属 + 广播适配」问题，**不是分布式一致性问题**。

### 模块边界（在单体内就划清）

```
@dt/shared   —— 纯逻辑，零 IO，可独立测试、可被 web 引入
@dt/server   —— 网络、房间、持久化、鉴权
@dt/web      —— 渲染
```

用 ESLint `no-restricted-imports` 强制边界（尤其 `web/src/views/**` 禁引 engine）。**边界是代码级而非进程级的**——这既拿到模块化的好处，又不付分布式的税。

## 备选方案

| 方案 | 优点 | 为什么不选 |
|---|---|---|
| **A. 一开始就拆微服务**（matchmaking / game / auth / replay 独立进程） | 独立伸缩、独立部署、故障隔离 | ① 团队规模下运维成本（服务发现、链路追踪、分布式日志、部署编排）会吃掉大部分工期；② 本作各模块耦合紧密（房间要调引擎、要写持久化、要广播），拆开后**跨服务调用比进程内调用多一个数量级的复杂度**；③ 负载根本不需要独立伸缩（matchmaking 与 game 的量级同比例增长）；④ 规则引擎同构复用会因为服务边界受损 |
| **B. 拆成两个服务：有状态 game 服务 + 无状态 API 服务** | 稍微合理一些 | 仍然引入部署与联调成本，而 MVP 的 API 面极小（登录、房间列表、对局历史）。等 API 面真正变大时再拆，成本更低 |
| **C. Serverless（Cloudflare Durable Objects / AWS Lambda + API GW WS）** | 免运维、按量付费、天然伸缩 | ① Durable Objects 的 WebSocket + 内存状态模型其实很契合本项目，但把运行时锁定到 Cloudflare，且本地开发与调试体验差；② 冷启动与长连接计费模型对 15–30 分钟的对局不友好；③ 引擎同构 + 回放 CLI 在 serverless 下更麻烦。**可作为未来托管形态候选，但 MVP 不冒这个锁定风险** |
| **D. 单体但内部无边界（一个大 src/ 目录）** | 最省事 | 会在 M2 后迅速腐化：前端不小心引了引擎、服务端逻辑渗进 shared、测试无从下手。ESLint 边界的成本只有几十行配置，**收益远大于成本** |

## 理由

1. **负载根本不需要拆分**：1v1 卡牌对战是低吞吐长连接。一台 2 核机器可承载数千并发对局（瓶颈是内存与带宽，不是 CPU 分片）。拆服务的驱动力不存在。
2. **房间 Actor 串行化把「扩展」变成「路由」问题**，这是本 ADR 的核心洞察。把这个前提在 M1 落地，未来的扩展路径就是确定的、低成本的。
3. **模块化单体的边界是代码级的**：ESLint 强制的 import 边界，在防腐化上的效果接近进程边界，成本却低两个数量级。
4. **同构复用优先**：`shared` 包被 web 与 server 同时引入，单体内是零成本的；跨服务就要走 npm 包版本管理 + 兼容矩阵。
5. **lean**：省下的时间投入规则引擎与内容数据（这才是本项目的真正难点，主文档 B4）。

## 后果与风险

**正面**

- 部署极简：`node dist/index.js` + 静态资源。
- 本地开发：一个 `pnpm dev` 起全部。
- 调试：单进程内完整堆栈，无跨服务追踪。
- 测试：集成测试可真实起服务 + 2 客户端，不需要 docker-compose。

**负面 / 需管理**

| 风险 | 缓解 |
|---|---|
| **房间 Actor 串行化前提没落地 → 未来扩展要重构** | M1 前必须完成 C3（MatchActor 串行队列）；加一条集成测试 I3（并发 50 意图 → seq 严格递增、无撕裂） |
| **单点故障：进程崩溃全部对局中断** | MVP 接受（ADR-005 R1）；P2 做快照恢复；多实例部署可彻底解决 |
| **单进程内存上限** | 每局 < 50KB × 数千局 = 数百 MB，安全；加内存监控与对局数上限（超过则拒绝新对局而非 OOM） |
| **未来拆服务时仍有工作量** | 已通过模块边界 + `MatchRepo`/`Transport` 接口把耦合点收敛到少数几个接口；预计拆分工作量 < 1 周 |
| **所有人都能改所有代码 → 边界腐化** | ESLint 边界规则进 CI required；code review checklist 含「是否跨越了包边界」 |

## 复核触发条件（任一满足即评审）

| 触发条件 | 动作 |
|---|---|
| 需要 >1 个 Node 实例（CPU 瓶颈或可用区冗余） | 引入 `@socket.io/redis-adapter`；房间按 `hash(roomId) % instances` 或集中路由表固定归属 |
| 需要进程重启不丢局 | Redis 作为房间状态热存储（写穿），或 Postgres + 快照（ADR-005 E5） |
| 匹配排队超过单实例承载 | 匹配队列移入 Redis（ZSET by rating）；可拆为独立 matchmaking 服务 |
| 需要跨区部署 / 灰度发布 | 引入网关层 + 房间路由表 |
| API 面显著增长（排行榜、社交、商城） | 拆出无状态 API 服务（方案 B） |
| 团队规模 > 5 人、需要独立发布节奏 | 按模块边界拆服务（此时边界已经在代码里，拆分成本最低） |
