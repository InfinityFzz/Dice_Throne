# ADR-002：权威与同步模型

- **状态**：Accepted
- **日期**：2025-xx-xx（架构基线）
- **决策者**：程基岩（engineering-lead）
- **相关**：ADR-001（传输）、ADR-003（引擎范式）、主文档 §2.2 / §2.3

## 背景

DT-Web 的对局存在**强信息不对称**：手牌内容、牌库顺序、未掷出的骰子结果对对手隐藏。这是桌游的核心乐趣来源，也是电子化后**最大的作弊攻击面**。同时：

- 规则复杂度极高（4 英雄 × 9 能力 × 20 卡 × 链式 then 效果 × 同时结算），规则实现**只能有一份**，否则必然漂移。
- 移动端要求操作即时反馈，但不能以牺牲正确性为代价。
- 需要支持断线重连、观战（未来）、回放。

核心问题是三个：

1. **谁是真相源？**（服务端 / 客户端协商 / 客户端自治 + 服务端校验）
2. **同步什么？**（全量状态 / 增量 diff / 事件 / 投影）
3. **客户端能不能预测？**（乐观更新 / 悲观）

## 决策

**服务端权威 + 全量 `GameState` 仅存在于服务端 + per-seat 结构化白名单投影（`PlayerView`）+ 服务端下发 `legalActions` + 客户端仅做视觉层乐观反馈。**

### 决策 1：服务端是唯一真相源

- `GameState` 只在服务端进程内实例化。客户端**在类型层面**拿不到它（只导入 `PlayerView` 与类型）。
- 客户端发送的是**意图（Action）**，不是结果。
- 服务端用同一份 `reduce()` 做校验与执行（见 ADR-003），非法意图 → `Err(RuleError)`，**状态不变**，回一帧 `game:rejected{ code }`。

### 决策 2：同步 per-seat 结构化投影，不做状态全量同步

```ts
projectState(state: GameState, viewer: Seat): PlayerView
```

- `PlayerView` 是**独立定义的结构**（白名单 mapper），不是 `GameState` 的深拷贝 + 删除。
- 选择白名单而非黑名单的理由：**fail-safe vs fail-open**。黑名单漏一个字段 = 直接泄密且不易被测到；白名单漏一个字段 = UI 少显示信息，会被测试与 E2E 立刻发现。在防作弊是硬需求的场景，必须 fail-safe。
- 事件侧同理：每个 `GameEvent` 带 `visibility: {v:'public'} | {v:'seat',seat} | {v:'server'}`，广播前过滤。

### 决策 3：`legalActions` 由服务端枚举并下发

`PlayerView.self.legalActions: Action[]` —— 服务端用引擎枚举当前玩家可执行的全部动作。

- 前端按钮禁用逻辑退化为一次集合查找，**不可能出现前端诱导出的非法操作**。
- 前端不需要复制任何规则判断 → 天然满足「UI 不持有游戏状态」。
- 枚举实现复用 `reduce()`：对候选动作试跑，成功即合法（不可变 + 结构共享，成本极低，动作空间 < 50）。
- **一份规则实现，三个用途：校验、执行、枚举。**

### 决策 4：客户端只做视觉层乐观反馈

- 允许：点击后立刻本地高亮/置灰、动画预播（例如点「锁定」骰子立刻反色）。
- 不允许：本地改动任何模型数值（HP/CP/手牌数）。
- 服务端回帧后以服务端为准覆盖（投影是幂等全量，`game:patch` 直接替换 view）。
- 若被拒绝：回滚视觉 + toast 提示 `RuleError.code`。

### 决策 5：不做增量 diff（至少 MVP 不做）

- 每次动作后下发**完整 `PlayerView`** + 本次新增事件。MVP 状态 < 50KB，gzip 后 < 8KB，每秒最多 1–2 帧。增量 diff 带来的复杂度（版本向量、补丁顺序、补丁丢失恢复）收益为负。
- 重连 = 下发一次完整快照，无状态追赶逻辑。

## 备选方案

| 方案 | 描述 | 为什么不选 |
|---|---|---|
| **A. 状态全量同步（服务端算完广播同一份 state，客户端自行隐藏）** | 实现最简单，一份 state 两边都有 | **不可接受**：客户端内存里就有对手手牌，等于把防作弊完全交给前端自觉。任何浏览器扩展/内存修改工具都能看到。这是本项目的头号风险（主文档 R2） |
| **B. 锁步确定性同步（Lockstep，只同步 input）** | 两端各跑一份引擎，服务端只转发输入 | 理论优雅（带宽最省），但：① 两端引擎版本必须逐位一致，任何版本漂移立即 desync 且难定位；② 客户端内存仍有全量状态 → 同 A 的作弊问题；③ 断线重连需要从头重放。**风险远大于收益** |
| **C. 乐观更新 + 服务端最终校验（Rollback）** | 客户端先改，服务端驳回则回滚 | 回合制不是 FPS，操作频率极低，乐观更新带来的体感收益接近零；而回滚逻辑（尤其是链式结算后的回滚）是本引擎最复杂的部分之一。得不偿失 |
| **D. 客户端自治 + 服务端抽样校验** | 客户端算，服务端抽查 | 完全不可接受。规则复杂 → 客户端实现必然与服务端漂移 → 玩家可构造合法外观的非法结果 |
| **E. 只同步事件流，客户端自行 fold 出视图** | 事件即同步单位 | 需要客户端有一份 `fold` 实现 = 客户端必须理解全部规则 = 客户端能算出全量状态（含对手手牌）。且重连要做快照 + 追赶。与我们的目标冲突 |
| **F. 权威服务端 + per-seat 增量 diff** | 本决策的复杂化版 | 见决策 5：MVP 收益为负。可在 M3 若帧体积成为问题时再评估 |

## 理由

1. **正确性 > 一切**：规则复杂度决定了「规则实现只能有一份」。服务端权威是最直接的实现方式。
2. **防作弊是硬需求**：信息不对称是玩法核心。任何把全量状态放到客户端的方案（A/B/C/E）都被排除，剩下的问题只是「投影怎么做」。
3. **白名单投影把泄密从「运行时风险」变成「类型系统约束」**：`PlayerView` 没有 `rng`、`deck`、`queue`、`ledger` 字段，客户端代码根本写不出读取它们的代码。
4. **`legalActions` 下发把「前端规则逻辑」从 N 处收敛到 0 处**：这既减少 bug，又让「新增卡牌/能力」不需要改前端——与「数据驱动」目标一致。
5. **全量投影 > 增量 diff**：lean 阶段的正确选择。状态小、帧率低、无追赶逻辑、重连一行搞定。
6. **放弃乐观更新的收益可忽略**：回合制下玩家决策本身就要思考数秒，<100ms 的往返延迟完全无感。

## 后果与风险

**正面**

- 客户端极薄：`PlayerView` 渲染 + `legalActions` 门控 + 事件动画。
- 新增英雄/卡牌不需要改前端（效果由服务端解析，前端只渲染事件）。
- 防作弊面收敛到「投影 mapper + 事件 visibility 过滤」两处，可被属性测试完整覆盖（主文档 T14 / I1）。
- 断线重连 = 一次全量快照，无状态追赶。

**负面 / 需管理**

| 风险 | 缓解 |
|---|---|
| **投影 mapper 写错导致泄密**（唯一的核心风险） | ① 白名单（fail-safe）；② T14 属性测试：500 组随机 state × viewer，断言 JSON 中不含对手 hand uid / 任何 deck uid / seed；③ I1 在**传输层**再断言一次；④ code review 必查 mapper diff |
| 每次动作都发全量 view，带宽略高 | MVP 状态 < 50KB/帧，gzip 后 < 8KB；可接受。加帧大小监控，> 256KB 告警 |
| 前端无法做「本地 AI 提示 / 概率计算」 | 允许在 `web/src/sandbox/**` 中跑本地引擎副本做推演，**结果不得回传**，且用本地 PRNG（与服务端无关）。ESLint 强制 `views/**` 禁引 engine |
| 等待服务端往返期间 UI 有轻微延迟 | 视觉层乐观反馈（决策 4）已覆盖 |
| `legalActions` 枚举若与 `reduce` 漂移会产生「按钮可点但被拒」 | 两者复用同一 `reduce`（决策 3），从根上消除漂移；再加属性测试断言 `∀ a ∈ legalActions: reduce(s,a).ok === true` |
| 未来加观战功能时，投影需要第三种视角 | `projectState` 的 `viewer` 参数已经是抽象点，加 `viewer: Seat | 'spectator'` 即可，spectator 视图 = 双方都是 `OpponentPlayerView` |

## 落地检查项

- [ ] `PlayerView` / `OpponentPlayerView` / `SharedView` 独立定义（不 `extends PlayerState`）
- [ ] `projectState` 为显式 mapper，逐字段搬运；禁止 `{...player}` 展开
- [ ] `GameEvent.visibility` 在广播前过滤，单测覆盖三种 visibility
- [ ] `enumerateLegalActions` 与 `reduce` 一致性属性测试
- [ ] T14 投影泄漏属性测试进入 CI required
- [ ] I1 传输层泄漏断言进入集成测试
- [ ] ESLint：`web/src/views/**` 禁止 import `@dt/shared/engine`
- [ ] `game:patch` 帧大小监控与告警阈值

## 复核触发条件

- 单帧 `PlayerView` 超过 256KB（→ 评估增量 diff）
- 需要观战 / 录制直播（→ 扩展 `viewer` 类型）
- 出现实际作弊事件（→ 复审投影 mapper 与 visibility 过滤，并增加运行时审计：服务端记录每帧下发内容的哈希）
