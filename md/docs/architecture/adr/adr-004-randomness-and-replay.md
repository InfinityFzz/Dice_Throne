# ADR-004：随机性与可复现

- **状态**：Accepted（附 1 项待 design 确认：Wild 面参与顺子的规则，主文档附录 B-3）
- **日期**：2025-xx-xx（架构基线）
- **决策者**：程基岩（engineering-lead）
- **相关**：ADR-003（引擎范式）、ADR-005（持久化与回放）

## 背景

游戏中所有随机性来源：

1. 开局：决定先手（若规则为随机）
2. 洗牌（开局 + 牌库耗尽重洗）
3. 进攻掷骰（每回合最多 3 次 × 5 颗）
4. 防守掷骰（N 颗，一次性）
5. 部分效果：随机弃牌、随机选骰、随机目标

诉求：

- **可回放**：一份录像必须能逐帧重演出完全相同的过程。
- **可测试**：单测必须能固定骰子序列，否则无法写稳定的规则测试。
- **防预知**：客户端绝不能从任何下发数据中推断出未来的骰值或牌库顺序（这是作弊面，主文档 R2）。
- **不预掷**：服务端不能提前把「这回合 3 次掷骰结果」都算好存着（那样内存里就有未来信息，一旦投影有漏洞就全泄；且灵活度差）。
- **跨端一致**：引擎在 Node 与浏览器都要跑，随机数必须逐位一致。

## 决策

**服务端生成种子，使用自带的 sfc32 PRNG，通过「命名流（named stream）+ 计数器」派生随机数；状态存在 `GameState.rng` 中；种子与未来随机值绝不下发客户端。**

### 决策 1：种子只在服务端生成

```ts
export interface RngState {
  readonly seed: string;                               // 服务端 crypto 生成（hex）
  readonly counters: Readonly<Record<string, number>>;  // 命名流各自独立计数
}
```

- 种子由服务端 `crypto.randomBytes(16).toString('hex')` 生成，写入初始 `GameState`。
- **客户端永不收到 `rng`**（`PlayerView` 白名单天然排除，ADR-002）。
- 客户端本地推演/AI 使用**自己的**本地种子，与对局无关、不影响服务端状态。

### 决策 2：命名流 + 计数器派生，不缓存 PRNG 对象

```ts
function nextU32(stream: string, s: RngState): [value: number, next: RngState]
```

流命名：`setup`、`shuffle:0`、`shuffle:1`、`dice:0`、`dice:1`、`misc`。

实现：
```
state_bits = splitmix32( hash(seed, stream) )   // 派生该流的初始状态
state_bits = advance(state_bits, counter)        // sfc32 前进 counter 步
value      = sfc32_output(state_bits)
next       = { seed, counters: { [stream]: counter + 1 } }
```

**不缓存 PRNG 实例**（对象不可序列化）。每次调用重新派生。5 骰 × 3 次 × 100 回合 = 1500 次调用，派生开销可忽略（每次约几十纳秒）。

**为什么分流**：① 回放时若某条流多消耗一次（例如新增了一次洗牌），只有该流错位，其他流结果仍可比对，便于定位回归；② 避免「掷骰消耗」隐式影响「牌库顺序」这类耦合；③ 便于写「只固定骰子、牌库随机」的定向测试。

### 决策 3：算法用自带 sfc32，不引第三方 PRNG 包

- sfc32：4×32bit 状态，纯 32 位整数运算，无 BigInt，周期 ≈ 2³²–2⁴³，通过 PractRand 级别的统计测试，质量对游戏足够。
- **理由**：跨端（Node V8 / 浏览器 V8/SpiderMonkey/JSC）与未来可能的非 JS 重放服务必须逐位一致。自带 30 行实现，依赖零，行为完全可控。第三方包可能引入 Float64/BigInt 或版本差异，且不受我们控制。
- 不用 `Math.random()`（不可种子化、引擎规范不保证跨实现一致）。
- 不用 64 位 PCG/xoshiro（JS 需 BigInt，慢且易写错）。

### 决策 4：不预掷——随机值在需要时才生成

- 骰值在 `rollDice` action 执行的那一刻从 `state.rng` 派生并写入 `DiceState.values`。
- 牌库在 `setup` 与 `reshuffle` 时洗一次，之后是确定的数组顺序（抽牌只是 `shift`）。
- **结果：物理上不存在「未来的骰子/牌序」**。即使投影出现漏洞，也没有未来信息可泄。这是防预知最彻底的做法（优于「预存 + 严格隐藏」）。

### 决策 5：洗牌用 Fisher–Yates（从后往前）

- 用 `shuffle:<seat>` 流；牌库抽空时重洗弃牌堆，消耗同一流的下一批数，产出 `deckReshuffled` 事件（公开，因为弃牌堆公开）。
- 不做「更公平的真随机」：会破坏可回放，且对游戏体验无实际增益（种子化 PRNG 的统计性质已足够好）。

### 决策 6：回放 = seed + actionLog，不存事件流

- `MatchRecord = { seed, setup, actions[] }`（含 `sys:` 内部动作）。
- 回放器从 seed 重建初始状态，逐条 apply actions，产出的事件流驱动动画。
- 不存事件流的理由：事件流是 actionLog 的函数，存它是冗余且会随引擎版本漂移（见 ADR-005）。

## 备选方案

| 方案 | 优点 | 为什么不选 |
|---|---|---|
| **A. `Math.random()` / `crypto.randomBytes` 直接用** | 零实现成本 | 不可复现 → 回放/确定性测试/反作弊审计全部失效。**直接否决** |
| **B. 引入 npm PRNG 包（如 `seedrandom`、`pure-rand`）** | 现成、有测试 | 跨端逐位一致性不受我们控制；`seedrandom` 依赖浮点运算（不同引擎的 Math 实现可能有 ulp 差异）；引入依赖换取 30 行代码不划算 |
| **C. 服务端预生成整局随机序列，切片下发** | 实现简单，一次生成 | ① 服务端内存里就有全部未来信息 → 投影一旦有漏洞就是灾难级泄密；② 无法处理「效果导致的额外掷骰」（序列长度不定）；③ 重洗/随机弃牌次数不定。**与防预知目标直接冲突** |
| **D. 客户端生成随机数并上报（客户端掷骰）** | 无服务端随机压力 | 完全不可接受：客户端可自选结果。作弊敞口 |
| **E. Commit–Reveal 协议（服务端承诺哈希，事后揭示种子）** | 密码学上可证明公平 | ① 回合制卡牌对战无需此级保证（无赌注场景）；② 会显著增加协议复杂度；③ 揭示后种子公开 = 未来牌局若复用种子则泄密。**收益远低于成本**。可作为未来「排位赛公证」的增强项，不进 MVP |
| **F. 单条全局流（不分命名流）** | 更简单 | 一次消耗错位会让后续全部随机数错位，回放定位困难；也无法做定向固定测试 |
| **G. 用 UUID/哈希（如 `sha256(seed + counter)`）取模** | 密码学安全、无状态 | 慢 2–3 个数量级（每次调用一次 SHA）；对游戏随机性无必要。sfc32 已足够 |

## 理由

1. **可回放要求随机必须是 state 的纯函数**。种子进 state + 计数器进 state = 随机是确定的。
2. **防预知的最优解是「不存在未来信息」**（决策 4），而不是「藏好未来信息」。这是本 ADR 最重要的判断。
3. **跨端逐位一致**要求算法简单、纯整数、无实现差异 → sfc32 自带实现。
4. **命名流是低成本高收益**：几乎不增加复杂度，却大幅提升回放回归的定位能力与测试的可定向性。
5. **lean**：总计约 40 行实现（sfc32 + 派生 + 洗牌 + 掷骰），无依赖。

## 后果与风险

**正面**

- 回放可做到「终局状态哈希一致」，成为最强的回归测试（T15）。
- 单测可精确构造骰子序列（`runScript` 固定 seed），规则测试稳定。
- 客户端无种子、无未来值 → 预知类作弊在架构层被消除。
- 无外部依赖，跨端行为完全可控。

**负面 / 需管理**

| 风险 | 缓解 |
|---|---|
| **sfc32 周期较短（2³²–2⁴³）**，极端长局理论上可能循环 | 单局随机消耗 < 10⁴ 次，远低于周期；且每局新种子。无需处理 |
| **分流的派生函数若写错会产生相关性**（不同流结果相同/相关） | 单测断言：同 seed 不同流的前 1000 个输出不相同；不同 seed 同流不相同；卡方检验基础分布均匀性 |
| **引擎改动导致随机消耗次数变化 → 旧回放失效** | `engineVersion` 记录；回放时校验版本，MVP 拒绝跨版本回放（ADR-005） |
| **玩家可通过大量对局反推种子**（理论可能） | ① 客户端不收到种子；② 但客户端能观察到自己的牌序/骰值——理论上可反推。缓解：种子 128 位，反推计算不可行；且即使推出种子也无法改变已发生的对局。**风险为低，记录备案** |
| **Wild 面参与顺子的规则未定 → 骰型判定与随机无关但影响可达性** | 主文档附录 B-3，默认「可充当任意值」；待 design 确认 |
| **重洗时是否重置流/计数器** | 明确：不重置，`shuffle:<seat>` 流持续递增。写进控制清单避免歧义 |
| 未来若加「随机目标」（>2 人） | 加 `targeting` 流即可，机制已预留 |

## 复核触发条件

- 需要「可证明公平」的公证能力（排位赛/锦标赛）→ 评估 Commit–Reveal（方案 E）作为增强
- 出现任何回放不一致的真实案例 → 立即停下做根因分析，不得绕过
- 需要 2–6 人扩展（新增 targeting 流）
